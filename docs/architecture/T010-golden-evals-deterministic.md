# T010: Deterministic Golden Evals for Analytical AI

## Technical Goal

Implement an automated, deterministic Golden Evaluation (Golden Evals) framework
to prevent mathematical hallucinations and "Prompt Drift" in the Sales Data Analysis Agent.
The system will run a curated benchmark dataset of natural language queries, intercept
the intermediate structured payloads returned by the tools, and assert exact mathematical
matches (with float tolerance) against ground-truth values before the LLM generates
its conversational response. This suite will be integrated into the CI/CD pipeline
as a mandatory quality gate.

## Architecture Decisions (ADRs)

### ADR-01: Interception-Based Deterministic Evaluation

- **Decision:** The evaluation harness will assert against the structured JSON data payload returned by the agent's internal tools (e.g., Domain Tools, SecuredSQLQueryTool) rather than evaluating the final natural language text generated by the LLM.
- **Alternatives Evaluated:**
  - *LLM-as-a-Judge:* Using another LLM prompt to grade the output. Rejected because it is probabilistic, non-deterministic, computationally expensive, and unsuitable for strict financial math.
  - *Regex/Keyword Matching on Output:* Extracting numbers from the final text. Rejected because LLM formatting varies (e.g., "$1,000.00" vs "1000 reais"), causing fragile tests.
- **Trade-offs:** Requires deep inspection of the LangChain/LangGraph agent execution trace to capture tool outputs. However, this guarantees 100% mathematical determinism, isolating the LLM's reasoning capabilities from its mathematical generation capabilities.

### ADR-02: Externalized JSON Benchmark Dataset

- **Decision:** The ground-truth test cases will be stored externally in `tests/evals/golden_dataset.json` rather than hardcoded in Python test files.
- **Rationale:** Allows non-engineers (e.g., Data Analysts, Product Managers) to add new benchmark queries and ground-truth values without modifying code. Ensures a clean separation of data and test execution logic.

### ADR-03: Float Tolerance Assertions

- **Decision:** The deterministic assertion engine will utilize `math.isclose()` (or `pytest.approx()`) for all numerical comparisons with strict configured tolerances (`abs_tol=0.01` for currency, `rel_tol=1e-3` for percentages/coefficients).
- **Rationale:** Floating-point arithmetic in Python and DuckDB can produce negligible precision variations (e.g., `100.0000000001` vs `100.0`). Strict equality (`==`) would lead to false-positive test failures.

### ADR-04: Pytest as the Evaluation Runner

- **Decision:** The evaluation framework will be built natively on top of `pytest`, utilizing `pytest.mark.parametrize` to dynamically generate test cases from the JSON dataset.
- **Rationale:** Integrates natively into the existing Python test infrastructure. Provides out-of-the-box parallelization (`pytest-xdist`), structured CI reporting, and fixture management.

## Security and Reliability

### Security Mitigations

- **Data Isolation:** The evaluation suite must run against a fixed, reproducible SQLite/DuckDB test fixture (e.g., `tests/fixtures/eval_dataset.csv`) ensuring evaluations never touch production data and remain hermetic.

### Reliability

- **Transient Error Handling:** The Pytest evaluation runner must implement retry logic (e.g., via `tenacity` or a custom loop) to handle transient `429 Too Many Requests` or `50X` errors from the OpenAI/LLM API, preventing flaky CI builds.

## Task Detailing (Summary Tasks)

### Task 001 - [Config]: Create the golden_dataset.json benchmark dataset

- **Phase:** 1
- **Depends On:** —
- **Parallel With:** Task 002
- **Objective:** Establish the declarative JSON file that acts as the source of truth for all mathematical evaluations.
- **Files/Path:** `tests/evals/golden_dataset.json`
- **Reuse:** None.
- **Technical Acceptance Criteria:**
  - Create a valid JSON array containing at least 5 canonical test cases.
  - Each record must include: `eval_id`, `category`, `question`, `expected_tool`, and `expected_metrics` (key-value mapping of floats/strings).

---

### Task 002 - [Domain-Model]: Create GoldenEvalRecord validation models

- **Phase:** 1
- **Depends On:** —
- **Parallel With:** Task 001
- **Objective:** Define strict Pydantic or Dataclass models to parse and validate the JSON benchmark dataset.
- **Files/Path:** `tests/evals/eval_models.py`
- **Reuse:** None.
- **Technical Acceptance Criteria:**
  - Create `GoldenEvalRecord` representing a single test case.
  - Include validation to ensure `expected_metrics` keys match known tool output signatures.

---

### Task 003 - [Test-Integration]: Implement Agent Interceptor to capture tool calls

- **Phase:** 2
- **Depends On:** Task 002
- **Parallel With:** Task 004
- **Objective:** Hook into the LangChain/LangGraph execution cycle to extract the name of the tool invoked and the raw JSON output it returned, before the final text generation.
- **Files/Path:** `tests/evals/interceptor.py` (or within the test file)
- **Reuse:** None.
- **Technical Acceptance Criteria:**
  - Implement a LangChain callback handler (e.g., `BaseCallbackHandler`) or inspect the `AgentExecutor` intermediate steps trace.
  - Expose a method to retrieve the `actual_tool_name` and the `parsed_tool_output` (dictionary) after an agent run completes.

---

### Task 004 - [Test-Integration]: Implement Deterministic Assertion Engine

- **Phase:** 2
- **Depends On:** Task 002
- **Parallel With:** Task 003
- **Objective:** Create a modular assertion utility that compares `expected_metrics` against the `parsed_tool_output` using strict float tolerances.
- **Files/Path:** `tests/evals/assertions.py` (or within the test file)
- **Reuse:** Python `math.isclose` or `pytest.approx`.
- **Technical Acceptance Criteria:**
  - Create function `assert_metrics_match(expected: dict, actual: dict)`.
  - Traverse all keys in `expected`. If the value is a float, assert equality using `math.isclose(actual, expected, abs_tol=0.01)`.
  - Format clear `AssertionError` messages detailing exactly which key failed, the expected value, and the actual value.

---

### Task 005 - [Test-Integration]: Implement test_golden_evals.py test runner

- **Phase:** 2
- **Depends On:** Task 003, Task 004
- **Parallel With:** —
- **Objective:** Orchestrate the Pytest execution loop, parameterizing over the JSON dataset and asserting results.
- **Files/Path:** `tests/evals/test_golden_evals.py`
- **Reuse:** Existing `SalesAgent` instantiation fixtures.
- **Technical Acceptance Criteria:**
  - Load `golden_dataset.json`.
  - Use `@pytest.mark.parametrize` to generate one test per `eval_id`.
  - For each test:
    1. Send `question` to the agent.
    2. Use the interceptor (Task 003) to capture tool execution.
    3. Assert `actual_tool_name == expected_tool`.
    4. Assert `parsed_tool_output` matches `expected_metrics` using the engine (Task 004).
  - Implement retry logic (e.g., using `tenacity`) for LLM API connection errors/rate limits during the test.

---
